# 🎓 Learn English Bot

Telegram-бот-викторина для изучения английского языка ([@fastapiwb_bot](https://t.me/fastapiwb_bot)) с полноценной панелью администрирования.

Проект прошёл путь от простого скрипта, читавшего слова из `.txt`-файлов, до сервиса с базой данных, веб-интерфейсом управления контентом, авторизацией и готовой к развёртыванию Docker-инфраструктурой.

## Возможности

- **Игровая механика**: викторина по переводу слов с подсказками, несколько уровней сложности, режим "все уровни вперемешку", персональная статистика игрока
- **Управление контентом без правки кода**: администратор добавляет и редактирует слова через веб-интерфейс — либо построчно в табличной админке, либо большим текстовым блоком (быстрый ввод/правка десятков слов сразу)
- **Многопользовательская авторизация**: несколько администраторских аккаунтов с хэшированными паролями, доступ к панели управления защищён логином
- **Готовность к продакшену**: конфигурация через переменные окружения, две Docker-конфигурации (разработка и продакшен), PostgreSQL, reverse-proxy на nginx

## Архитектура и технические решения

| Слой | Технология | Почему так |
|---|---|---|
| Backend / Admin API | **FastAPI** | асинхронный, автогенерация OpenAPI-документации (`/docs`), типизация через Pydantic |
| ORM / доступ к данным | **SQLAlchemy 2.0** | единый слой данных, общий и для API, и для бота; смена БД — это смена одной строки конфигурации, а не переписывание кода |
| База данных | **SQLite** (разработка) / **PostgreSQL** (Docker, продакшен) | быстрый старт без внешних зависимостей локально, промышленная СУБД в контейнерах — идентичное поведение на всех этапах |
| Админ-панель | **SQLAdmin** | готовая табличная CRUD-панель поверх моделей SQLAlchemy, без написания фронтенда с нуля |
| Массовый редактор контента | Собственный модуль на FastAPI + Jinja-подобный рендеринг | доменная задача (сотни слов на уровень) не покрывалась стандартной админкой — написан отдельный "блокнотный" редактор поверх той же бизнес-логики |
| Аутентификация | **bcrypt** + подписанные cookie-сессии (**itsdangerous**) | пароли только в виде хэша, сессии не хранятся на сервере (stateless), собственная реализация без лишних зависимостей |
| Конфигурация | **python-dotenv**, 12-factor подход | секреты (токен, ключ подписи) никогда не хранятся в коде и не попадают в git |
| Бот | **pyTelegramBotAPI** | полностью на общей бизнес-логике с Admin API — правки контента видны боту без перезапуска |
| Контейнеризация | **Docker + Docker Compose**, отдельные конфигурации для dev/prod | окружение разработки воспроизводимо одной командой; продакшен-конфигурация изолирует БД от внешнего доступа и убирает live-монтирование кода |
| Reverse-proxy | **nginx** | точка входа для будущего SSL-терминирования (Let's Encrypt) |

### Ключевые инженерные решения

**Отказ от файлового хранения контента.** Изначальная версия бота хранила словарные базы в текстовых файлах на диске — любое изменение требовало доступа к файловой системе сервера и перезапуска процесса. Контент вынесен в реляционную БД с нормализованной схемой (`Level` → `Question`, один-ко-многим), что открыло путь к веб-редактированию, множественным одновременным правкам и валидации данных на уровне схемы.

**Единый слой бизнес-логики.** Функции работы с данными (`app/crud.py`) переиспользуются и в Admin API, и в телеграм-боте — правило "одна функция, одно место истины" исключает рассинхронизацию поведения между интерфейсами.

**Постепенная миграция без простоя.** Переход от `key.py`/файлового конфига к переменным окружения (`.env`) и от SQLite к PostgreSQL сделан с сохранением обратной совместимости на каждом шаге — старые способы запуска продолжали работать, пока новые не были полностью протестированы.

**Docker как граница окружений.** Конфигурация для разработки монтирует код как volume и запускает `uvicorn --reload`; продакшен-конфигурация собирает самодостаточный образ без внешних зависимостей от хост-файловой системы и без публичного порта у базы данных — типичная практика для промышленного развёртывания.

## Установка и запуск

Ниже — пошаговая инструкция для локального запуска (без Docker и через Docker) и для развёртывания на сервере.

### Стек

- **FastAPI** — Admin API + веб-страницы управления
- **SQLAdmin** — веб-админка поверх БД (таблицы, формы, поиск)
- **SQLAlchemy** — работа с базой данных
- **SQLite** (без Docker) / **PostgreSQL** (в Docker) — база данных
- **pyTelegramBotAPI (telebot)** — сам телеграм-бот, режим polling
- **bcrypt** — хэширование паролей аккаунтов админки
- **python-dotenv** — секреты (токен, ключ сессий) из `.env`, не из кода
- **Docker + docker-compose** — контейнеризация (опционально, см. ниже)

Есть два способа запуска: **без Docker** (Python + venv, база — файл
SQLite, см. ниже) и **через Docker** (см. раздел "Docker" в конце —
там же PostgreSQL и продакшен-вариант с nginx).

## Установка (Windows, PowerShell)

Открой папку проекта в PowerShell или в терминале VS Code и выполни по порядку:

```powershell
# 1. Создать виртуальное окружение
python -m venv .venv

# 2. Активировать его
.venv\Scripts\activate

# 3. Установить зависимости
pip install -r requirements.txt
```

Если `python` не находится — установи Python 3.11+ с python.org и поставь
галочку "Add python.exe to PATH" при установке.

## Первый запуск

### 0. Настройка секретов (.env)

Скопируй `.env.example` в `.env`:

```powershell
Copy-Item .env.example .env
```

Открой `.env` и впиши токен бота (полученный от
[@BotFather](https://t.me/BotFather)):

```
BOT_TOKEN=твой_токен_от_botfather
```

`SECRET_KEY` можно оставить пустым — сгенерируется автоматически при
первом запуске. Файл `.env` уже в `.gitignore` и никогда не должен
попадать в git.

Если у тебя ещё остался старый `key.py` с токеном — можно его удалить,
он больше не используется, если `.env` настроен (но специально ломать
ничего не будет: пока `.env` не создан, токен по-прежнему подхватится
из `key.py`, если он есть).

### 1. Перенос старых вопросов в базу (один раз)

В папке `txt/` лежат старые файлы с вопросами. Чтобы перенести их в базу:

```powershell
python scripts\seed_from_txt.py
```

Скрипт создаст файл `english_bot.db` и заполнит его уровнями и вопросами.
Повторный запуск ничего не сломает — уровни, которые уже есть, пропускаются.

### 2. Создание аккаунта для входа в админку (один раз)

```powershell
python scripts\create_admin.py
```

Спросит логин и пароль в консоли (ввод пароля скрыт). Можно запускать
ещё раз с тем же логином, чтобы сменить пароль, или с другим логином,
чтобы создать ещё один аккаунт.

## Запуск Admin API + веб-интерфейсов

```powershell
python run_api.py
```

Всё, что ниже, требует входа — открыв любой адрес без логина, тебя
перекинет на страницу входа.

### 📝 /manage — редактор слов (рекомендуется для повседневной работы)

**http://127.0.0.1:8000/manage**

- список всех уровней с количеством слов в каждом
- **«+ Новый уровень»** — создать уровень (key латиницей + название)
- **«Список слов»** — открывает уровень целиком одним текстом в формате
  `слово | перевод | подсказка`, одна строка = одно слово. Правишь текст
  как обычный блокнот (дописал/удалил/поправил строку) и жмёшь
  «Сохранить» — весь список слов уровня в базе заменяется на то, что
  получилось. Перевод можно указывать несколько вариантов через `/`.
- **«Переименовать»** — изменить отображаемое имя и описание уровня
- **«Удалить»** — удалить уровень со всеми его словами целиком (спросит
  подтверждение, действие необратимо)

### 🖥️ /admin — обычная табличная админка (для точечных правок)

**http://127.0.0.1:8000/admin**

Классический интерфейс: разделы **Уровни** и **Вопросы**, можно искать,
редактировать и удалять отдельные записи по одной, фильтровать вопросы
по уровню. Удобна, когда нужно поправить/удалить одно конкретное слово,
а не весь список разом.

### 📋 /docs — API-документация

Для программного доступа или массовой вставки вопросов через прямой
HTTP-запрос (`POST /levels/{level_id}/questions/bulk`).

## Запуск бота

В **отдельном** окне терминала:

```powershell
.venv\Scripts\activate
python run_bot.py
```

Бот подключится к Telegram и начнёт отвечать на сообщения. Останавливается
через Ctrl+C. Новые уровни/слова, добавленные через `/manage` или `/admin`,
подхватываются ботом сразу — перезапускать его не обязательно.

## Структура проекта

```
Learn_English_TgBot/
├── app/
│   ├── database.py    # подключение к SQLite
│   ├── models.py      # модели Level, Question, AdminUser

│   ├── crud.py         # функции работы с БД (общие для API и бота)
│   ├── parser.py        # парсер текста "слово|ответ|подсказка"
│   ├── auth.py            # хэширование паролей, cookie-сессии
│   ├── admin.py            # настройка веб-админки SQLAdmin (с логином)
│   ├── manage.py            # "блокнотный" редактор слов (с логином)
│   └── api.py                 # FastAPI-приложение, сборка всего вместе
├── bot/
│   └── bot.py                 # телеграм-бот
├── scripts/
│   ├── seed_from_txt.py       # разовый импорт старых .txt файлов в БД
│   └── create_admin.py        # создание/сброс пароля аккаунта админки
├── txt/                        # старые файлы с вопросами (для миграции)
├── key.py                      # токен бота (не должен попадать в git)
├── .secret_key                 # ключ для подписи сессий (создаётся сам, не в git)
├── requirements.txt
├── run_api.py
└── run_bot.py
```

## Про авторизацию

Логин защищает и `/manage`, и `/admin` — оба используют одну и ту же
таблицу аккаунтов (`admin_users`) в базе, пароли хранятся только в виде
bcrypt-хэша, никогда открытым текстом.

Ключ для подписи сессионных cookie при первом запуске сохраняется в файл
`.secret_key` рядом с проектом (в `.gitignore`, в репозиторий не
попадает) — так вход не будет слетать при каждом перезапуске сервера.
Если файл удалить, все залогиненные до этого сессии станут
недействительными, и надо будет войти заново — это не страшно.

Чтобы добавить ещё одного человека с доступом к админке — просто ещё раз
`python scripts\create_admin.py` с другим логином. Чтобы отозвать доступ —
через `/admin` можно снять галочку `is_active` у аккаунта в разделе БД,
либо попросить пересоздать пароль.

## Добавление нового уровня — пример

**Через /manage (рекомендуется):**

1. Открой `http://127.0.0.1:8000/manage`, войди под своим логином.
2. Впиши `key=food`, `name=🍎 Еда` → «+ Новый уровень».
3. Откроется пустой редактор — вставь весь список слов сразу:
   ```
   apple | яблоко | red or green fruit
   bread | хлеб | you eat it every day
   ```
4. «Сохранить».

**Через API** (для скриптовой/массовой загрузки):

1. Открой `http://127.0.0.1:8000/docs`.
2. `POST /levels`: `{"key": "food", "name": "🍎 Еда"}`.
3. `POST /levels/{id}/questions/bulk`: `{"text": "apple | яблоко | ..."}`.

## О безопасности токена

Файл `key.py` с токеном бота добавлен в `.gitignore` — он не должен
попадать в git-репозиторий или куда-либо ещё, где его смогут увидеть
посторонние. Если токен всё же где-то засветился — можно бесплатно
перевыпустить его через [@BotFather](https://t.me/BotFather) командой
`/mybots` → выбрать бота → `API Token` → `Revoke current token`.

## Docker

Два варианта: **локальная разработка** (`docker-compose.yml`) и
**продакшен-каркас** (`docker-compose.prod.yml`). Оба используют
PostgreSQL вместо SQLite — так поведение локально и на сервере
одинаковое, без сюрпризов при переезде.

### Установка Docker Desktop (Windows)

Если ещё не установлен:

1. Скачай с [docker.com/products/docker-desktop](https://www.docker.com/products/docker-desktop/).
2. Установи и перезапусти компьютер, если попросит.
3. При первом запуске Docker Desktop спросит про WSL 2 — соглашайся,
   это стандартный и самый быстрый способ запускать Linux-контейнеры на
   Windows. Если WSL 2 не установлена, Docker Desktop сам подскажет
   команду для установки (`wsl --install`) — выполни её в PowerShell от
   администратора, перезагрузись и открой Docker Desktop снова.
4. Дождись, пока иконка Docker в трее станет "зелёной" (Engine running).
5. Проверь в PowerShell:
   ```powershell
   docker --version
   docker compose version
   ```

### Локальный запуск через Docker

1. Скопируй `.env.example` в `.env` (если ещё не делал) и впиши
   `BOT_TOKEN`. Значения `POSTGRES_*` можно оставить по умолчанию —
   для локальной разработки они не критичны.
2. Из корня проекта:
   ```powershell
   docker compose up --build
   ```
3. Подожди, пока соберётся образ и поднимутся все три контейнера
   (`db`, `api`, `bot`) — в логе появится `Application startup complete`
   и `Бот запущен...`.
4. Открой `http://localhost:8000/manage` — так же, как при запуске без
   Docker, только теперь всё работает в контейнерах, а данные хранятся
   в PostgreSQL.
5. Если это первый запуск — база пустая, нужно один раз выполнить
   миграцию старых слов и создать аккаунт админки **внутри контейнера
   api**:
   ```powershell
   docker compose exec api python scripts/seed_from_txt.py
   docker compose exec api python scripts/create_admin.py
   ```
6. Остановить всё: `Ctrl+C`, затем `docker compose down` (данные в
   PostgreSQL остаются — они лежат в отдельном Docker volume `pgdata` и
   переживают остановку контейнеров; `docker compose down -v` удалит и
   их тоже, если понадобится начать с чистого листа).

Правки в коде на хосте (в VS Code) подхватываются автоматически —
код примонтирован в контейнер, `uvicorn --reload` перезапускает Admin
API сам. Для бота автоперезапуска нет (Telegram-библиотека этого не
поддерживает) — после правок в `bot/`: `docker compose restart bot`.

### Продакшен-каркас

`docker-compose.prod.yml` — то же самое, но:
- код НЕ примонтирован (образ самодостаточен — что собрано, то и
  работает, никакой рассинхронизации с хостом);
- PostgreSQL не пробрасывает порт наружу (доступна только другим
  контейнерам, не всему интернету);
- добавлен **nginx** как reverse-proxy на 80 порту (`nginx/nginx.conf`).

Это ещё **не готовый к использованию продакшен** — сначала нужен
реальный сервер (VPS) и домен. Запуск на сервере:

```bash
# .env на сервере ОБЯЗАН содержать свои значения — не используй
# пароль "english_bot" из примера, сгенерируй боевой SECRET_KEY:
python3 -c "import secrets; print(secrets.token_hex(32))"

docker compose -f docker-compose.prod.yml up --build -d
docker compose -f docker-compose.prod.yml exec api python scripts/seed_from_txt.py
docker compose -f docker-compose.prod.yml exec api python scripts/create_admin.py
```

### Следующий шаг: домен и HTTPS

Сейчас `nginx/nginx.conf` — просто reverse-proxy без сертификата.
Когда будет реальный сервер с доменом, туда добавляется блок для
Let's Encrypt (`certbot`) и редирект с 80 на 443 — это отдельный шаг,
не хочешь ли заняться им — просто скажи, когда дойдёт до реального
сервера.
